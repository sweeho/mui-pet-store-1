# Design — Bootstrap, landing page and shared site shell

## Context

This change is generated by the platform for every migration and greenfield initiative (architecture doc 41). The capability brief canvas, its wireframes and its mockups are the detailed design; this document records the decisions every other capability relies on.

## Decisions

- **One shell.** Every page renders inside the same layout, header, navigation and footer. A capability adds content to the shell; it never draws its own chrome.
- **One navigation.** The global navigation lists every primary area and always links back to the landing page. A capability that adds a primary area adds one entry here rather than a second menu.
- **Shared states.** Empty, error and loading frames are components of the shell, reused by every page.
- **Existing boilerplate wins.** Where the repository already has an application scaffold, extend it rather than scaffold again.
- **Sign-in only if the product has it.** The shell carries a sign-in frame only when the product requirements call for authentication.

## Primary areas

- Order fulfilment and invoicing (`order-fulfilment`)
- Administration of orders (`admin-order-management`)

### Codebase findings

- **Shell exists.** `src/app/(DashboardLayout)/layout.tsx` wraps every page in `DashboardShell` (`src/shell/`): `Sidebar` (270px, permanent Drawer at `lg`+, temporary Drawer below), `Header` (MUI `AppBar` → `<header>`, only a menu button) and a `<main>` box. There is **no footer**.
- **Navigation** is `MENU_ITEMS` in `src/shell/SidebarItems.tsx`: one entry, Home `/`, inside `<List component="nav">`. The brand link above it reads `APP_NAME` (`src/constants/app.ts`, currently `mui-pet-store-1`, also used for the document title in `src/app/layout.tsx`).
- **Root route** `src/app/(DashboardLayout)/page.tsx` renders the template's `HomeView` ("Hello, world" + `findUser(1)`). `e2e/home.spec.ts`, `e2e/smoke.spec.ts` and `src/components/HomeView.test.tsx` assert that template content.
- **No shared frames, no `error.tsx` or `loading.tsx`** exist anywhere under `src/app/`.
- **Locked acceptance suite** `tests/acceptance/site-shell/` fixes these contracts:
  - the first `navigation` landmark on a page is the global navigation; every nav href other than `/` must also be a link inside `<main>` on `/`; every nav href must open a page with `banner`, `navigation`, `main` and `contentinfo`, `main` sitting between header and footer;
  - `HomePage()` from `src/app/(DashboardLayout)/page.tsx` is an async server component that loads through `findUser` from `@/lib/users`; when the load resolves `null` it renders an element with `data-testid="empty-frame"`; when the load rejects, `HomePage()` rejects;
  - `src/app/(DashboardLayout)/error.tsx` default-exports `({ error, reset })` rendering `data-testid="error-frame"` and a button named Retry that calls `reset` once.
- **Routes other capabilities' locked suites already use:** `/catalog`, `/cart`, `/signon`, `/admin/inventory` (Inventory screen), `/admin` and `/admin/login`. The navigation targets these exact paths so later capabilities replace a placeholder page rather than move a link.
- **CI** (`.github/workflows/ci.yml`) runs on pull requests to `vortex/**`, `dev`, `main` and pushes to `dev`, `main`; acceptance steps are `continue-on-error` while other capabilities' suites are red. No change is needed this sprint.

### Spec discrepancies

- **D1 — Primary areas.** `proposal.md` and the "Primary areas" list above name two areas (`order-fulfilment`, `admin-order-management`). The approved brief and mockups show five (Catalog & search, Cart, Sign on, Order fulfilment and invoicing, Administration of orders) plus Home. The build follows the brief and mockups; the delta spec is unaffected because its scenarios say "every primary area".
- **D2 — Landing page data load.** The spec's landing page has no data, but locked test SWHM2-C-0228/0229 exercise the shared frames through the real `HomePage` and its `findUser` load (template demo data). The landing page therefore keeps that load; with seeded data the tiles show, with no row it shows the empty frame. A later capability may replace the load with real landing data.
- **D3 — Sidebar width.** Template sidebar is 270px; the brief and mockups require 240px. The build uses 240px (DESIGN.md updated).
- **D4 — Header controls and loading frame** (language control, Sign on / Create account, loading frame) appear in the brief and mockups but in no scenario or test case. They are built as inert placeholders; their behaviour belongs to customer-accounts and internationalisation.
